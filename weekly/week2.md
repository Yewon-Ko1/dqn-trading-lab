# Week 2 회고 (2026-09-03 ~ 2026-09-09) — 환경과 에이전트 구현

> 학습 흐름: 데이터·평가 기준 → **환경·에이전트 구현** → 원리 정리와 검증 설계 → 설정 동결과 최종 평가

앞 주에 만든 데이터와 기준선 위에서 동작하는 매매 환경을 정의하고, DQN과 Double DQN을 직접 구현해 walk-forward 실험까지 연결한 주간입니다. 최신 진행 상태는 루트 [`README.md`](../README.md), 실험 결정은 [`decisions.md`](../decisions.md)를 기준으로 합니다.

## 이번 주 목표

- 매매 문제를 강화학습 문제로 정의하고(상태·행동·보상), 학습이 실제로 일어나는지 확인한다.

## 완료한 작업

### 매매 환경

- 상태 정의 — 최근 window일 피처와 포지션 3종(주식 비중·누적 손익·현금 비중)
- 행동 정의 — 매수·매도·보유. 현금이나 보유 주식이 없으면 해당 행동을 보유로 처리(액션 마스킹)
- 보상 정의 — 거래비용을 반영한 일별 자산 변화율
- 거래비용 반영 — 수수료 0.015%(양방향), 매도 거래세 0.25%
- 랜덤 에이전트로 환경 자체를 먼저 검증한 뒤 학습 코드로 진행

### 에이전트

- PyTorch Q-network — 입력 → 은닉 2층(ReLU) → 행동 3개의 Q값, 출력층에는 활성화 함수를 두지 않음
- DQN — Replay Buffer, Target Network, ε-greedy 탐험, 매 스텝 TD 학습, Smooth L1 손실, Adam
- Double DQN — 행동 선택은 온라인 네트워크, 가치 평가는 타깃 네트워크로 분리
- 단계별 검사 스크립트로 각 구현의 동작을 확인한 뒤 다음 단계로 진행

### 실험 실행기

- 테스트 연도별로 기준선 4종을 함께 기록하고, 설정·시드·성과를 CSV에 누적하며 시드별 자산 곡선 그림을 생성
- 삼성전자와 KODEX 200에 대해 2021~2024년 4개 폴드 × 시드 5개로 Basic DQN과 Double DQN 비교
- 단일 학습 스크립트와 정책 저장 경로 구성

### 팀 백엔드 연동 설계

- 팀 백엔드 구조 분석 — 정책 인터페이스와 등록 방식, 주문 전 리스크 게이트, 증권사·시뮬레이터를 교체할 수 있는 브로커 계층
- 연동 시 생기는 차이 세 가지 정리 — 피처 정의(비율형 대 원지표), 학습에 사용한 정규화 통계를 모델 파일과 함께 저장해야 하는 점, 포지션 상태 변수의 대응 관계
- 위 내용을 반영한 정책 어댑터 초안 작성

## 배운 점

- 보상을 일별 자산 변화율로 두면 에피소드 동안의 보상 누적(복리)이 최종 자산과 일치한다. 보상 정의가 곧 목적함수다.
- 타깃 네트워크가 없으면 학습 목표가 매 스텝 함께 움직여 Q값이 발산하기 쉽다. 목표를 일정 주기 고정하는 것이 학습 안정성의 핵심이다.
- Double DQN은 최댓값 연산이 만드는 Q값 과대평가를 줄이기 위한 구조이지, 수익률을 직접 올리는 장치가 아니다.
- 학습 환경과 운영 환경의 피처·정규화 정의가 어긋나면 모델 성능과 무관하게 실패한다.
