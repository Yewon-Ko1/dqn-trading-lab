# 04. 매매 환경(TradingEnv) — 강화학습의 "게임판" 만들기

> **rltrader에서는:** `environment.py`(차트를 한 칸씩 보여줌) + `agent.py`(잔고 관리, act, validate_action)
> 두 파일이 하던 일을 우리는 클래스 하나로 합친다. 팀 backend의 `rl/env/trading_env.py`가 같은 구조다.

## 0. 먼저: 클래스(class)가 뭔가

지금까지 만든 건 전부 **함수** — 넣으면 나오는 기계였다. 그런데 매매 환경은 함수로 만들기 어렵다.
"현재 잔고가 얼마고, 주식을 몇 주 들고 있고, 오늘이 며칠째인지"를 **계속 기억하면서** 움직여야 하기 때문이다.

**클래스 = 데이터(기억)와 함수(동작)를 한 묶음으로 가진 설계도.** 게임 캐릭터를 생각하면 된다:
캐릭터는 HP·소지금(데이터)을 갖고 있고, 공격하기·아이템사기(동작)를 할 수 있다.

```python
class TradingEnv:                      # 설계도 선언
    def __init__(self, df, ...):       # 생성자: env = TradingEnv(df) 할 때 한 번 실행됨
        self.balance = 10_000_000      # self.무엇 = 이 객체가 기억하는 데이터
    def step(self, action):            # 메서드: 이 객체가 할 수 있는 동작
        self.balance -= ...            # 동작 안에서 기억을 읽고 바꾼다
```

- `self` = "나 자신". 메서드 첫 파라미터에 항상 쓰고, 부를 때는 안 넣는다 (`env.step(0)` ← self 자동).
- `self.balance` = 객체에 붙은 변수(속성). 함수가 끝나도 **사라지지 않고 유지된다.** 이게 클래스를 쓰는 이유.
- `env = TradingEnv(df)` = 설계도로 실물 하나를 찍어내는 것(객체 생성). `__init__`이 이때 실행된다.

## 1. 강화학습의 4요소 — 이 클래스가 정의하는 것

| 요소 | 뜻 | 우리 환경에서 |
|---|---|---|
| **state (상태)** | 에이전트가 매일 아침 보는 것 | 최근 20일 피처를 한 줄로 편 것 + 내 포지션 3개(보유비율·수익률·잔고비율) |
| **action (행동)** | 고를 수 있는 선택지 | 0=매수(BUY), 1=매도(SELL), 2=관망(HOLD) |
| **reward (보상)** | 행동 직후 받는 점수 | 하루 재산 변화율: `오늘 자산/어제 자산 − 1` (비용 반영됨) |
| **episode (판)** | 게임 한 판 | 데이터 첫날~마지막 날까지 한 바퀴. 끝나면 done=True |

여기가 **문제 정의** 그 자체다. state에 무엇을 넣고 reward를 무엇으로 하느냐가
"모델이 무엇을 잘하도록 배울 것인가"를 결정한다. DQN 코드(07)는 이 정의를 바꾸지 않는다 —
정의가 틀리면 아무리 잘 학습해도 엉뚱한 걸 잘하게 된다.

포지션 3개를 state에 넣는 이유: 같은 차트라도 "주식을 들고 있냐 아니냐"에 따라 최적 행동이 다르다.
rltrader의 `agent.get_states()`와 같은 발상이다.

## 2. step() 한 번 = 하루의 흐름

```
step(action) 이 하는 일 (순서 중요):
1) 오늘 가격으로 행동 집행
   BUY : 현금으로 살 수 있는 만큼 매수 (수수료 반영). 현금 부족하면 아무 일 없음
   SELL: 보유 전량 매도 (수수료+거래세 차감). 0주면 아무 일 없음
   HOLD: 아무것도 안 함
2) 하루 전진 (t += 1)
3) 새 자산 평가: 현금 + 주식수 × 내일 가격
4) reward = 새 자산 / 어제 자산 − 1
5) done = 데이터 끝에 닿았나
6) 새 state 반환
```

"현금 부족한데 BUY", "0주인데 SELL"을 조용히 HOLD로 바꾸는 걸 **액션 마스킹**이라 한다.
불가능한 행동으로 학습이 망가지는 걸 막는 안전장치다 (rltrader의 `validate_action`과 같은 역할).

## 3. 환경이 지켜야 할 불변 법칙 (check_04가 검사하는 것)

1. 잔고와 보유 주식 수는 **절대 음수가 되지 않는다.**
2. 관망만 하면 자산은 정확히 초기자본 그대로다 (공짜 수익도 공짜 손실도 없음).
3. 보상을 전부 누적하면(복리로 곱하면) 정확히 최종 자산과 일치한다 — 보상이 곧 돈이다.
4. 매수→가격 2배→매도 같은 손계산 시나리오와 코드 결과가 일치한다 (수수료·세금 포함).

이 법칙들이 지켜지지 않는 환경에서 학습한 모델의 성과는 전부 무의미하다.
그래서 05단계(랜덤 에이전트 검증)가 따로 있는 것이다.

## 자주 하는 실수

- reset을 안 하고 두 판째를 돌림 → 잔고가 이전 판 것 그대로 (reset이 초기화 담당)
- reward를 "가격 변화율"로 계산 → 주식이 없는 날에도 보상이 생기는 버그. **자산** 변화율이어야 함
- 매수 가능 주식 수를 나눗셈(`/`)으로 계산 → 소수 주식 매수. 몫(`//`)과 int 필요
- step 순서 바꿈 (하루 전진을 먼저 하고 어제 가격으로 매매) → 하루 밀린 체결
